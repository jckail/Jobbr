# Owner-approved extension capture

The capture protocol uses the existing website Sign in with ChatGPT session. It does not register another OpenAI OAuth client, share website cookies with the popup, or grant access to profiles, drafts, job details, application notes or normal website writes. Configure the non-secret `JOBBR_EXTENSION_ALLOWED_IDS` as a comma-separated list of reviewed, stable installed Chrome extension IDs. The default empty list disables authorization; malformed lists fail closed. An ID, Origin header and comparison code are public labels, not proof of publisher identity. PKCE and the opaque bearer capability provide the possession proofs.

The popup generates a random PKCE verifier locally. It opens the configured website destination with the extension ID and S256 challenge in the fragment, never the verifier or bearer token. The owner compares the code shown in both places and explicitly reviews the extension ID, configured destination, capture scope and current provider/model/possible API charges. Website approval requires the existing owner session, exact website Origin and CSRF token. Only this approval creates a pairing row. Public challenge inspection and incorrect exchange requests create no rows, increment no counters, and do not acquire the shared mutation lock. Destination URLs come from the configured registered HTTPS callback origin plus the configured mount path, never request Host headers.

Approval starts a five-minute exchange window. A valid S256 verifier exchanges that pairing once for a random bearer capability; a consumed metadata tombstone prevents duplicate exchange or approval for the same challenge during that window. The capability lasts at most fifteen minutes and never outlives the approving session. It permits five capture reservations, one concurrent capture, and no refresh. Every exchange and capture checks the current auth scope, live approving session, expiry, reviewed extension ID and stored revocation state. Captures also pin all three AI settings to the approved policy and a settings snapshot passed through the actual extractor; a server policy change requires new review and authorization.

Authorization and receipt rows contain only hashes and metadata. No raw capability, PKCE verifier, posting text, resume, profile snapshot, provider response or application note is persisted in these tables. Pairings and grants are capped at 128 each, with at most 32 owner approvals per minute. These are shared transactional limits across processes. Unauthorized users cannot populate them because bootstrap writes require website approval. Normal request flooding still requires deployment-level availability controls; this protocol does not claim to prevent network denial of service.

Each capture requires a fresh opaque idempotency key. A durable reservation is committed before fetching or extracting the posting, including before any potentially paid provider call. Repeating an identical completed key returns only `{id}` without another extraction. A mismatched payload, pending or failed reservation is rejected. Failures consume a reservation; they are never retried automatically. A crash after saving a job but before marking its receipt complete has an unknown outcome: review Jobbr before initiating a new capture. No existing job title, company, score, profile or notes are returned to the extension.

Logout, website revocation, popup disconnect, expiry, configuration changes or removal of the allowed extension ID prevent future reservations. An already committed reservation may finish extracting and save its job after those events; revocation does not cancel a provider call already started. The reservation transaction locks the approving session so a concurrent logout cannot complete ahead of that reservation commit. Busy expired metadata is retained for a ten-minute completion grace, then pruned to bound dead-worker retention. Completed receipts are bounded by the five-reservation budget. These limits and behaviors are identical for SQLite local persistence and shared PostgreSQL deployments.

Owners can list and revoke grants from the website using owner-only session access; revocation writes require CSRF. The popup can disconnect only its own bearer grant, then forget its local capability. There is no general CORS or credential allowance: only the three exchange/capture/disconnect endpoints accept a reviewed `chrome-extension://ID` Origin, and responses never permit browser credentials. Neither this capability nor an extension Origin is accepted as website authentication.

Migration `0006_extension_capture` adds four metadata tables without modifying existing private content. Backup verification retains frozen `0005_tailoring` compatibility, and backups include capture metadata. Offline tests cover SQLite and, when `JOBBR_TEST_POSTGRES_URL` names the dedicated `jobbr_test` database, isolated PostgreSQL schemas. They simulate provider dispatch; they make no paid calls and do not establish live SIWC registration or Chrome acceptance.
